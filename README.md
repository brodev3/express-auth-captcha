# Сервис аутентификации с CAPTCHA

Тестовое веб-приложение с регистрацией, входом по username или email,
серверными сессиями, защищённым профилем, выходом из системы и одноразовой
математической CAPTCHA. Интерфейс отрисовывается на сервере и не требует
frontend-фреймворка.

Демо: [express-auth-captcha.onrender.com/login](https://express-auth-captcha.onrender.com/login)

## Возможности

- регистрация с независимой клиентской и серверной валидацией;
- уникальные username и email без учёта регистра;
- хеширование паролей через PBKDF2 из `node:crypto`;
- вход по username или email с единым сообщением об ошибке;
- одноразовая CAPTCHA, ответ которой хранится только в серверной сессии;
- серверные сессии в SQLite и пересоздание идентификатора после входа;
- защищённый профиль с email, датой регистрации и ролью пользователя;
- уничтожение сессии при выходе;
- русскоязычный тёмный интерфейс, адаптированный для мобильных устройств.

## Стек

- Node.js 22+, Express 5, TypeScript;
- EJS и vanilla HTML/CSS/JavaScript;
- SQLite, `sqlite3`, `connect-sqlite3`;
- Vitest и Supertest;
- ESLint.

## Быстрый старт

Потребуются Node.js версии 22 или новее и npm.

```bash
npm ci
```

Создайте `.env` на основе `.env.example` и замените `SESSION_SECRET` случайной
строкой длиной не менее 32 символов. Например, безопасное значение можно
сгенерировать командой:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Запуск в режиме разработки:

```bash
npm run dev
```

Приложение по умолчанию доступно по адресу
[`http://localhost:3000`](http://localhost:3000). Миграции запускаются
автоматически при старте, а SQLite-файл создаётся в `data/app.sqlite`.

Для запуска собранной версии:

```bash
npm run build
npm start
```

При `NODE_ENV=production` cookie сессии имеет флаг `Secure`, поэтому такой
режим предполагает HTTPS.

## Конфигурация

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `NODE_ENV` | `development` | `development`, `test` или `production` |
| `PORT` | `3000` | HTTP-порт приложения |
| `DATABASE_PATH` | `data/app.sqlite` | Путь к SQLite-файлу или `:memory:` для тестов |
| `SESSION_SECRET` | нет | Секрет подписи cookie, минимум 32 символа; обязателен вне тестов |

Файл `.env` не должен попадать в Git.

## Маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/` | Переход на страницу входа или в профиль |
| `GET`, `POST` | `/register` | Регистрация пользователя |
| `GET`, `POST` | `/login` | Вход по username или email |
| `GET` | `/profile` | Защищённая страница профиля |
| `POST` | `/logout` | Завершение сессии |
| `GET` | `/health` | Проверка доступности процесса |

## Проверки

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

Тесты используют временные SQLite-базы и проверяют валидацию, CAPTCHA,
регистрацию, вход, сессии, контроль доступа, профиль и logout.

## Устройство проекта

```text
src/auth/      маршруты, валидация, сервис и repository пользователей
src/captcha/   выдача и одноразовая проверка CAPTCHA
src/db/        SQLite-адаптер и запуск миграций
src/web/       сессии и flash-сообщения
views/         EJS-шаблоны
public/        клиентские CSS и JavaScript
migrations/    версионированная схема SQLite
tests/         модульные и интеграционные тесты
```

Контроллеры принимают HTTP-запросы и формируют ответы, бизнес-правила находятся
в сервисах, а SQL изолирован в слое доступа к данным. Пользовательские значения
передаются в SQLite параметрами и выводятся через экранирующий синтаксис EJS.

## Безопасность

- пароль хранится как версионированный PBKDF2-HMAC-SHA256 хеш с уникальной
  солью и 600 000 итераций;
- для неизвестного пользователя выполняется фиктивная проверка хеша;
- после входа сессия пересоздаётся для защиты от session fixation;
- cookie содержит только непрозрачный идентификатор и имеет `HttpOnly`,
  `SameSite=Lax`, срок жизни 2 часа и `Secure` в production;
- CAPTCHA действует 5 минут, привязана к форме и удаляется при первой проверке;
- размер URL-encoded тела запроса ограничен 10 КБ;
- внутренние ошибки, SQL и stack trace не показываются пользователю.

Полные проверяемые условия находятся в
[требованиях и критериях приёмки](docs/requirements.md).

## Ограничения

Это компактная реализация тестового задания, а не готовая публичная система.
В неё намеренно не входят внешняя CAPTCHA, rate limiting, отдельные CSRF-токены,
подтверждение email, восстановление пароля, MFA, аудит событий, Redis,
multi-instance deployment и HTTPS termination. Для реальной эксплуатации эти
механизмы потребовалось бы добавить отдельно.
